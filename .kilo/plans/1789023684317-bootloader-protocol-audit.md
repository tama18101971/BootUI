## 1. Несоответствия протоколу (с привязкой к строкам)

### 1.1 [Критично] Баг разбора кадра READ в `Proteus32-BootLoader\proteus32_3.py` — `--dump` не работает

Эталон (прошивка), `User/iap.c:319-334` (`UART_Rx_Deal`, ветка `ERR_Read_Ok`):

```
AA 55 84 00 <64 Б data> CKL CKH 55 AA        — ровно 72 байта
байты:  0  1  2  3  4..67            68 69  70 71
```

Файл `Proteus32-BootLoader/proteus32_3.py`:

- `154`: docstring заявляет «76 bytes»;
- `159`: `expected_len = 6 + BLOCK_SIZE + 4` → **74**, а не 72;
- `173`: сверка контрольной суммы читает `buf[70]`/`buf[71]` — должно быть `buf[68]`/`buf[69]`;
- `175`: сверка хвоста читает `buf[72]`/`buf[73]` — должно быть `buf[70]`/`buf[71]`.

Следствие: `wait_read_response()` ждёт 74 байта, которых от прошивки никогда не придёт (она
шлёт ровно 72 и замолкает, ожидая следующий кадр — строгий stop-and-wait). Цикл в `168-170`
(`while ... if len(buf) >= expected_len: break`) не завершается досрочно и съедает весь
`timeout` (по умолчанию `TIMEOUT_CMD=3.0`) на каждую попытку. После истечения дедлайна —
`len(buf) < expected_len` → `"неполный кадр READ (получено 72 из 74 байт)"`. Команда `--dump`
у этой копии скрипта **не работает вообще ни на одном блоке** (3 попытки × 3 с = 9 с на блок,
затем `✗ READ failed`, exit-код 1). На основной цикл записи (ERASE/PROM/VERIFY/END) баг не
влияет — `wait_read_response` используется только в `cmd_dump`.

Тот же баг, побайтово, есть в `Proteus32/proteus32_3.py:153-177` (вне плана, см. §4).

**Уже исправлено** в `BootUI/proteus32_3.py:153-192` — там `wait_read_response()` корректно
считает 72-байтовый кадр (`min_len = 4 + BLOCK_SIZE + 4`) и дополнительно (защитно) допускает
76-байтовый вариант с 4-байтовым эхо-адресом перед данными, определяя раскладку по совпадению
контрольной суммы. Комментарий в коде (`156-157`) утверждает, что такой 76-байтовый вариант
«прошивался на некоторых стендах» — то есть, возможно, отражает поведение какой-то другой
(не входящей в текущий репозиторий) ревизии прошивки. Текущая `User/iap.c` этой ревизии
отправляет **только** 72-байтовый кадр без эхо-адреса.

### 1.2 [Незначительно] Несогласованный таймаут ожидания ACK на END в `BootUI/bootloader_gui.py`

`bootloader_gui.py:420`:
```python
ok, _status = parse_base_response(wait_response(ser, timeout=2.0))
```
Везде в файле используется `TIMEOUT_CMD = 3.0` (константа объявлена `bootloader_gui.py:39`,
используется в `send_packet`). Спецификация — `BOOTLOADER_TZ.md`, раздел 4.3, п.5: «END
(таймаут 3 с; ответ может не прийти... — не считать ошибкой)». Хардкод `2.0` — расхождение
с собственной константой файла и с ТЗ. Не критично (отсутствие ответа и так не считается
ошибкой), но следует привести к единому значению.

Для сравнения, в `BootUI/proteus32_3.py` эта же операция вынесена в отдельную функцию
`send_end_best_effort(ser, timeout=2.0)` (`232-229`... т.е. строки `218-229`) — то есть
несогласованность (`2.0` вместо `TIMEOUT_CMD`) продублирована и там; расхождение с ТЗ
одинаковое в обоих файлах BootUI.

### 1.3 [Незначительно, архитектурно] Дублирование протокольной логики между `bootloader_gui.py` и `proteus32_3.py` (BootUI)

Обе функции `make_packet`, `parse_base_response`, `wait_response`, `send_packet`,
`probe_protocol_v2` реализованы независимо в каждом файле (`bootloader_gui.py:44-165`,
`proteus32_3.py:81-243`). Это именно тот механизм, из-за которого правка READ-парсинга и
таймаута END была внесена в CLI-версию, но частично не попала в GUI (см. §1.2) — а в версии
Proteus32-BootLoader не попала вовсе (см. §1.1). Рекомендация — не блокирующая для текущего
фикса, см. план действий, пункт 3.

### 1.4 [Документация] `README.md:64` — таблица команд протокола сама себе противоречит по END

`README.md:64`:
```
| 0x83 | END | 0x00 (+4 Б addr, игнор.) | — | ACK, пауза ≥100 мс, сброс в приложение |
```
Текст утверждает, что END несёт (и игнорирует) 4 байта адреса. Однако:
- прошивка (`User/iap.c:287-298`, `UART_Rx_Deal`) читает 4 байта адреса-заглушки **только**
  для `CMD_IAP_ERASE`/`CMD_IAP_VERIFY`; `CMD_IAP_END` в этом условии не участвует;
- контрольный вектор двумя строками ниже в том же файле (`README.md:86`):
  `END: AA 55 83 00 83 00 55 AA` — контрольная сумма `83 00` = `Cmd(0x83)+Len(0x00)`, без
  каких-либо байт адреса (иначе сумма была бы `8B 00`).

Оба скрипта (BootUI и Proteus32-BootLoader) корректно следуют **коду и контрольному вектору**
(END без адресных байт: `proteus32_3.py:93-95`, `bootloader_gui.py:55-56`), а не ошибочной
строке таблицы — то есть текущий баг чисто документационный, но он представляет риск: правка
скрипта «по таблице» в будущем сломает контрольную сумму END на реальной прошивке. Аналогичная
формулировка есть в `BOOTLOADER_TZ.md` (раздел 3.5.2, строка про 0x83) — файл ТЗ трогать не
предлагается: репозиторий явно фиксирует «Дополнений к ТЗ нет» (`README.md:7`).

### 1.5 [Документация] `README.md:121-129` («Несовместимость версий») устарела относительно кода BootUI

Текст утверждает, что скрипт BootUI шлёт VERIFY с `Len=0` (no-op) и являет с этим несовместимость
с протоколом v2. Однако в текущем `bootloader_gui.py:60-63,394-410` VERIFY уже пересылает
настоящие 64 байта эталона — расхождение исторической причины несовместимости с текущим кодом
отсутствует. Раздел явно не актуален и должен быть переписан после фикса §1.1 (см. план,
пункт 4).

### 1.6 [Низкий приоритет, UX] `bootloader_gui.py` предлагает baud rate, не поддерживаемый прошивкой

`BAUD_RATES` (`bootloader_gui.py:41`) содержит 8 значений (9600…921600), выбираемых в
`baud_combo` (`215-222`). Прошивка использует фиксированный `USART1->BRR = 0x34`
(`User/iap.c:66`) при HSI 24 МГц — это соответствует ровно 460800 бод; иное значение SYSCLK/BRR
в прошивке не предусмотрено (`README.md:52`, `BOOTLOADER_TZ.md:515`: «Изменение SYSCLK сломает
BRR»). Выбор любого другого значения в выпадающем списке гарантированно даёт не работающий канал
связи без диагностируемой причины для пользователя. CLI-скрипт (`-b/--baudrate`, default
460800) в этом смысле безопаснее — переопределение требует явного флага, а не выбора из
готового списка со скрытым риском.

## 2. Подтверждённое соответствие протоколу (без замечаний)

Проверено побайтово по контрольным векторам `README.md:83-88` / `BOOTLOADER_TZ.md §3.5.4` —
совпадает в обоих актуальных файлах BootUI и в `Proteus32-BootLoader/proteus32_3.py`:

- формат кадра `AA 55 CMD LEN PAYLOAD CKL CKH 55 AA`, контрольная сумма
  `(CMD+LEN+ΣPAYLOAD) mod 0x10000`, little-endian — идентична во всех make_packet;
- ERASE — 4-байтовый адрес-заглушка после `Len=0`, входит в контрольную сумму;
- PROM — без адреса, `Len=0x40`, 64 байта данных;
- VERIFY — 4-байтовая заглушка + 64 байта эталона (в обеих версиях BootUI — реальные данные,
  не no-op);
- END — без адреса (см. также эрратум §1.4);
- базовый ответ `AA 55 00 ST 55 AA` (6 байт, `[2]` — константа, не эхо команды) — разбор
  идентичен прошивке;
- stop-and-wait, 3 повтора с `reset_input_buffer()`, таймауты 10 с (ERASE) / 3 с (прочее) —
  совпадают с `BOOTLOADER_TZ.md §3.5.5`;
- жёсткая проверка размера образа ≤ `0x3F00` (16128 Б) без `--force` — совпадает с
  `BOOTLOADER_TZ.md §4.2`;
- `PROTOCOL_REV = 2` маркировка в обоих файлах BootUI, хотя ТЗ требовало её явно только для
  `proteus32_3.py` — распространено и на GUI, что даже избыточно-хорошо.

     `BootUI/proteus32_3.py:153-192`) взамен текущей (`Proteus32-BootLoader/proteus32_3.py:153-177`).
   - Вместе с ней перенести также остальные накопленные в BootUI улучшения этого же файла,
     чтобы не тащить путаницу двух версий одного скрипта: `probe_protocol_v2`/`fail_no_v2`
     (проверка ревизии прошивки перед ERASE/END), `send_end_best_effort`, проверку
     `--len <= 0` в `cmd_dump`, проверку на пустой файл прошивки в `cmd_write`. Итоговый файл

     `proteus32_3.py` в BootUI. Это устранит корневую причину дрейфа между копиями (см. §1.3)

   - Решение по объёму этого рефакторинга — на усмотрение исполнителя/пользователя; не
